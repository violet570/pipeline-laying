## 三档规划模式（用户核心需求，2026-11-06 改版）

模式由用户在左栏自行选择（不再按点击次数自动推断）：

| 模式 | 用户给了什么 | 系统做什么 |
|---|---|---|
| **A · 全校（默认起点）** | 什么都不给 | 连接全部 45 个供水目标，起点沿用默认水源（南主门 / 7 号门）。与主数据那套方案一致：8,115.9 m / 468.3 万元 |
| **B · 选点排除** | 在左栏点建筑编号（可多选） | 把这些建筑移出方案，剩余建筑重新求全局最短铺设；起点在 5/6/7 号门中重新比选 |
| **C · 自定起点 + 多终点** | 图上点 1 个起点 + 若干终点 | **只铺这些点，不铺全校**：起点吸附路网后作水源，终点作为仅有的受水目标跑 MST（点楼=那栋楼带用水量，点空地=路网接入点）；还没点终点时不画管网 |

默认假设是南主门市政接入点——**这是假设，不是实测，页面上必须标出来**。

> 规划台与矩阵页共用同一套引擎 `06_代码/pipe_engine.js`，矩阵页**按当前页面选择实时重算**（不是固定画全校那套）；
> 规划台右上角「无向图 / 矩阵演示」会把当前模式 / 排除编号 / 起点 / 接入点带进 URL hash 同步过去。
> 详见 `06_代码/README_脚本说明.md` 的「规划台三模式」。

## 画面上必须有的东西

- **每栋供水建筑的接户三件套**：路边接入点（tee）+ 接户支管 + 立管与逐层出水口。不能只在主路上画一笔带过。
- **动画**：管道沿路网生长、水流方向流动、按铺设层级逐层展开、可重播。
- **两种视图**：2.5D 等轴测 / 平面。
- **底图可切换**：高德卫星 / 高德路网 / 纯矢量。
- **悬停明细**：楼名、类别、层数、面积、日用水、支管长度、来源路名、逐层口径、几何来源（OSM/影像量测）。
- **统计面板**：目标数、MST 总长、管道实长、总用水、设计流量、主干管径、最大树深、造价、接户点数。
- **方案对比**：MST vs 直线MST vs 星形，给出省了多少。
- **参数可调**：经济流速、Kh、层高、用水指标、管材单价——改完即时重算。

## 数据可信度：必须如实告诉使用者

这个项目的数据不是"完美"的，下面这些都是**已经写进报告和页面**的已知边界：

| 事项 | 状态 |
|---|---|
| 建筑轮廓 | 50 个来自 OSM 矢量，11 个来自影像量测（bbox 矩形代理）；`buildings[].parts` 保留全部 **78 个单体**轮廓，`footprint` 只保留主楼（兼容旧前端） |
| 多栋组团 | 1–11 组团各 2 栋、12/13 组团各 4 栋；`lat/lon` 是主楼代表点，不是组团质心（T05、T14 会落在轮廓外，属已知边界） |
| 圆形广场环路 | **OSM 没有，是从高德 z18 路网图的白色道路像素提取的**（5 条，标 `source=user_trace`）；2026-11-01 重描为 **120.3 m、72 顶点、首尾闭合**（v4），并用新的接户选边算法重算，见下 |
| 10 组建筑（Y01–Y11） | 只有楼名，**没有坐标，不参与计算** |
| 水源位置 | **假设**为南门市政接入点，OSM 无给水泵房数据 |
| 建筑层数 | 仅 9 栋有 OSM 标注，其余按类别默认 |
| 高德底图坐标 | **GCJ-02**，与计算用的 WGS-84 差约 529 m，必须转换 |
| 「图文信息楼」 | 已删除——原依据的 way id 经查不存在，且无法定位，不猜、不补 |

**踩过的最大坑**：曾经有 5 个 OSM way id 被误当作校园建筑，实际是美国北达科他州的乡村道路（北纬 46°）。教训是**批量抓取后必须按 id 回查 + 地理范围断言**。取证记录在 `04_数据/derived/id_validation.json`。

**第二大的坑：环路半径描小了一半，后来又描大了一圈。** 第一版描线用像素空间固定值 R=72 px ≈ 66 m；第二版把圆心南移约 60 m 后仍沿用旧圆心量到的 145 m，结果整圈比真实环道大 20%（环道顶点到高德道路中位偏 19 m、最大 33 m），而且首尾差了 36 m 没闭合。2026-11-01 用高德 z18 路网图（`05_图件/卫星与底图/amap_west.png`）的白色道路像素逐 1° 提取中心线，得到 **120.3 m、72 顶点、首尾闭合** 的 v4 环道（脚本 `06_代码/retrace_plaza_ring_v4.py`），并顺带修正了接户支管的选边算法（旧版只取"离建筑中心最近的边"，会把大 bbox 的支管算到背对道路的一侧）。三代对比：

| 建筑 | v1（r=66 m） | v2（r=145 m） | **v4（r=120.3 m，现行）** |
|---|---|---|---|
| 信息学院 | ~50 m | 28.4 m | **2.1 m** |
| 人工智能 | ~40 m | 125.5 m | **11.0 m** |
| 理学院 | 52.8 m | 54.1 m | **3.3 m** |
| 国际·生命健康 | 90.3 m | 52.7 m | **29.7 m**（接景行路） |
| 西里西亚学院 | 64.3 m | 59.3 m | **20.1 m** |

v4 之后接户支管中位数 **11.0 m**、最长 **103.8 m**（新体育馆）；校核图见 `05_图件/标注成果/ring_v3_v4_compare.jpg`（灰 = 旧 145 m，品红 = v4，底图高德路网）。

**人工智能的 125.5 m 是假距离，不是"物理上诚实的代价"。** 它站在广场正中没错，但 v4 环道从它 bbox 西侧约 11 m 处经过；旧算法把接户点选到了背对环道的东侧，才算出 107~125 m。修正后 11.0 m 与图上位置一致。

原始描线完整保留在 `04_数据/derived/plaza_roads_user_原始描线r66m.json`，v2 的 145 m 版本见 `05_图件/标注成果/ring_fit_overlay.jpg`（历史对照）。

## 一句话总结

**这件事的难点不在算法，在数据。** MST、Dijkstra、树形 DP 都是课本上的东西，真正的功夫是：把一栋一栋楼从卫星影像上认出来、把名字对上、把坐标较准、把 OSM 缺失的路补上、把每一个"这是假设"的地方老老实实标出来。这套物料就是把这些功夫固化下来，让写代码的人可以专心写代码。
