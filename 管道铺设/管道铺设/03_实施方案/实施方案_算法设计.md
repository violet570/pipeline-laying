## 0 一句话结论

用真实校园数据做管道铺设规划，**技术上完全可行，而且算法点足够扎实**：以校园路网为约束图、以建筑群为需求点，先用 **Dijkstra** 把"任意两点沿路网的真实敷设距离"全部算出来（预处理），再用 **Kruskal / Prim** 求最小生成树得到主干管网，然后在这棵树上做 **树形 DP** 分配管径与流量，最后用 **2.5D 轴测图**把方案画出来。

这套流程里，**三个算法各自解决一个不同的真问题**，不是硬凑：

| 算法 | 解决的问题 | 在本项目里的实际作用 |
|---|---|---|
| Dijkstra | 两点之间"沿路网"的最短敷设距离 | 把 45 个供水目标变成 990 条真实距离边（$\binom{46}{2}$，欧氏距离不可用，见 §2.3） |
| Kruskal / Prim | 连通的、总长最短的管网拓扑 | 主干管网走向，替代"星形直连"省 81% 的管长 |
| 树形 DP | 每段管子要多大、流量怎么分 | 管径分配 + 造价估算，体现"管道越靠近水源越粗"的工程直觉 |

**如果还要再加一个亮点**（答辩时最容易被追问的地方）：把单水源 MST 扩展为**多水源 / 单水源带容量约束 / 分期建设**三种场景，用 **DP 或拟阵（matroid）理论**说明 MST 的最优性边界——为什么 MST 在这一类问题上是"最优"的，什么情况下不是。

## 1 问题定义与建模

### 1.1 问题陈述

西校区有 N 个用水建筑群（学生公寓、食堂、教学楼、实验楼……），需要铺设给水管道把它们和市政给水接入点连起来，使得：

1. **连通性**：每个建筑群都能从水源取到水；
2. **管道只能沿道路敷设**（工程约束：不能穿楼、不能穿湖、不能穿操场）；
3. **总造价最低**（管材 + 土方 + 接口，主要随管长和管径增长）。

这是一个典型的**带路径约束的网络设计问题**，是 NP-hard 的 Steiner 树问题的特例，但在"沿路网 + 单水源 + 不考虑管径"的简化下，**最优解恰好是路网图上的最小生成树**（说明见 §2.2）。

### 1.2 形式化

定义无向图 $G = (V, E)$：

- $V$：**路网节点集合**。取 OSM 道路的折点，并在每个建筑群的接户点处"打断"路段插入新节点。实测西校区路网 $|V| = 955$。
- $E$：**路段集合**，$|E| = 1{,}067$。边权 $w(e) = \ell_e \cdot c_{\text{type}(e)}$，其中 $\ell_e$ 是路段实长（米），$c$ 是敷设难度系数：

  | 道路等级 | 权重系数 | 理由 |
  |---|---|---|
  | `unclassified`（校园主路） | 1.00 | 路面最好开挖 |
  | `tertiary` / `secondary` | 1.15 | 车行道，需夜间施工、交通导改 |
  | `residential` / `service` | 1.30 | 有路缘石、绿化带 |
  | `cycleway` / `footway` / `path` | 1.60 | 透水砖/铺装，恢复成本高 |
  | `steps` / `construction` | **排除** | 台阶不能开槽；在建路段不稳定 |

- 需求点集合 $T \subseteq V$，$|T| = 62$（已定位的建筑群；剩余 10 个待实测，不影响算法正确性）。
- 每个需求点 $t$ 有日用水量 $d_t$（由建筑面积 × 分类用水指标估算，见 §2.5）。

**目标**：求 $G$ 的一棵生成树 $T^*$（连通所有需求点与水源 $s$），使
$$\sum_{e \in T^*} w(e) \;=\; \min$$

### 1.3 为什么这不是一个"玩具问题"

三个真实约束让标准 MST 不能直接套：

1. **欧氏距离不可用**。两栋楼直线 80 m，中间隔着湖或者教学楼，实际要绕 400 m。用欧氏距离求 MST 得到的管网，**在真实路网上根本画不出来**（会穿楼）。
2. **需求点不在路网节点上**。建筑群中心不在道路上，要先把它们"投影"到最近路段并插入节点（§2.4），这一步直接决定管网拓扑是否合理。
3. **管径是分级的**。DN32 到 DN500 共 14 档标准公称直径，管径选择影响造价权重，反过来又会影响"哪条路更划算"——严格来说这是个**两级优化**，需要近似处理（§2.7）。

### 2.2 关键论证：为什么"路网 MST"是合理的最优解

这是答辩时最容易被问的点，必须能讲清楚。

**命题**：在"管道只能沿路网敷设、单水源、不考虑管径"的假设下，最优管网拓扑等价于路网图上的 Steiner 树问题；当所有需求点本身就是路网节点（已通过 §2.4 插入实现）时，Steiner 树退化为最小生成树，Kruskal 给出的解**精确最优**。

**证明思路（交换论证）**：

1. 任何可行管网必须使所有需求点与水源连通，因此在路网子图上包含一棵生成树；
2. 树的总长必然大于等于该点集的最小生成树长（MST 是所有生成树中总权最小的）；
3. 所以 MST 是可行解空间的**下界**，而 MST 本身是可行的，故最优。

**这个论证的边界在哪里（必须主动说明）**：

| 假设 | 现实中的偏差 | 影响 | 处理 |
|---|---|---|---|
| 单水源 | 校园可能有多个接入点 | MST 会变"单点故障" | §3.4 扩展为多水源 |
| 不考虑管径 | 管径影响造价权重 | 粗管段应尽量短 | §2.6 两级迭代 |
| 不考虑容量 | 主干管有最大流量限制 | 超限需并联或改径 | §3.4 容量约束版 |
| 需求点已在路网节点上 | 楼到路的接户支管 | 支管长度遗漏 | 已计入（§2.4） |

**答辩话术**："我们的 MST 不是随便套的，是在明确假设下严格最优；我们逐个列出了假设被破坏时的偏差方向和处理办法，并且实现了其中两个扩展版本。"

### 2.3 Dijkstra：把"绕路距离"算出来

**为什么必须做**：MST 的边权必须是真实敷设距离。如果直接用两栋楼的欧氏距离：

- 管网会穿过 燕大后海（水面）、穿越教学楼、跨越操场跑道；
- 实测对比：直线 MST 总长 **5,632.2 m**，沿路网 MST 总长 **8,115.9 m**——**差 2,483.7 m，多出 44.1%**。这不是精度问题，是"画不出来"的问题。

**实现**：二叉堆优化的 Dijkstra，复杂度 $O((V+E)\log V)$。每跑一次约 20 ms（1,035 节点 / 1,151 边），跑 46 次（水源 + 45 个需求点）总耗时约 1 s，完全可以接受。

**输出**：

- $D[i][j]$：需求点 $i$ 到 $j$ 的路网最短距离（46×46 矩阵；已导出为 `04_数据/derived/graph_matrix.txt`，页面 `05_图件/管道方案/matrix_mst.html` 直接读取该矩阵跑 Prim/Kruskal）；
- $D[s][i]$：水源到各需求点的距离；
- 每个 $D[i][j]$ 对应的**实际路径**（前驱数组回溯），后面画图要用。

> 实现踩坑记录（写进报告显得真实）：最初用 OSM way 的局部坐标建图，导致不同 way 之间不连通（只找到 7 个可达目标）。根因是**没有按经纬度合并共享节点**，改用全局坐标注册表 `coord_reg[(round(lat,7), round(lon,7))]` 后才正确。

### 2.4 需求点接入路网

**算法**：对每个建筑群质心 $p$，

1. 遍历所有路段（$|E| = 1{,}067$），求 $p$ 到线段的最近点；
2. 取距离最近的路段 $e^*$，得最近点 $q$ 与参数 $t^*$；
3. 若 $t^*$ 落在端点附近（$t < 10^{-4}$ 或 $t > 1 - 10^{-4}$），直接复用该端点；
4. 否则**在 $e^*$ 上插入新节点**：删除 $e^*$，加入 $(a, q)$ 和 $(q, b)$ 两条边，边权按长度比例分配；
5. 记录接户距离 $|p - q|$（这段是**垂直于道路的支管**，计入总造价）。

**实测结果**：45 个需求点全部成功接入。**最大接路距离 173.1 m**（西校区新体育馆）。原先最长的三个人工智能学院 227.9 m、理学院、信息学院，在按高德影像补描圆形广场环路后全部降到 100 m 以内——说明那一段确实是底图缺路，而不是算法选错了路。

> 这里踩过一个很隐蔽的坑：最初实现"无论是否分裂都删掉原边"，导致端点邻近的情况把边删了却没加回来，图被逐次破坏，出现 `UNREACH 29`、连通分量只有 8 个节点。修正后：**端点分支直接返回、不修改图**；只有真正的中点分裂才删边加边。

### 2.5 用水量估算

$$\text{日用水量} \; d_i \;=\; \text{建筑面积}_i \times \text{用水指标}_{c(i)} \qquad (\text{L/d})$$

用水指标参考《建筑给水排水设计标准》GB 50015 的宿舍/公共建筑定额量级，按本项目尺度取值：

| 类别 | 用水指标 L/(m²·d) | 依据 |
|---|---|---|
| 学生公寓 | 12.0 | 约 50 L/(人·d) ÷ 人均 4.2 m² 折算 |
| 食堂 | 40.0 | 含洗涤、备餐 |
| 服务楼（超市商业） | 8.0 | — |
| 教学楼 | 5.0 | — |
| 学院楼 | 5.0 | 按教学楼同档（含办公、实验、师生） |
| 办公楼 | 6.0 | — |
| 图书馆 | 5.0 | — |
| 体育场馆 | 3.0 | — |
| 实验楼 | 6.0 | — |
| 艺术场馆 | 3.0 | — |
| 活动中心 | 5.0 | — |
| 市政设施（变电站） | 2.0 | 仅生活用水 |
| 无名附属建筑 | — | **不供水**（见下） |

> **不计入供水目标的两类**：① `other` 无名附属建筑 15 栋（门卫房、车棚、配电间一类，单体 130~1752 m²）——用途未知且用水需求可忽略；② `utility` 变电站——强电设施，只需按需预留，不接入生活给水管网。二者仅作为背景建筑绘制在图上。

> ⚠ 这些指标是**量级正确的估算**，用于方案比较，不等于逐条查表。正式设计须以 GB 50015 原文与当地水务部门核定为准。报告中已如实标注。

**设计流量**：按最高日最高时流量计算。$K_h$ 的定义是"最高日最高时流量 ÷ 最高日平均时流量"，故

$$Q_{\max} = \frac{\sum d_i}{24}\times K_h \quad (\text{m}^3/\text{h}) \;=\; \frac{\sum d_i \cdot K_h}{24\times 3600} \quad (\text{L/s}), \qquad K_h = 2.5$$

实测：$\sum d_i = 6{,}887.4\ \text{m}^3/\text{d}$ → $Q_{\max} = \dfrac{6{,}887.4 \times 2.5}{24 \times 3600}\times 1000 = 199.29\ \text{L/s}$。

> 注：$\frac{K_h}{86400}$ 与 $\frac{K_h}{24\times3600}$ 数值相同（因 $86400=24\times3600$），两种写法等价，都可放心使用；关键是 **$K_h$ 必须乘以日总量，而不是乘以"平均秒流量"**。用"高峰等效小时数" $h_{peak}=24/K_h=9.6$ h 来理解最直观：全部日用水量集中在 9.6 小时内均匀用完，即得最高时流量。

### 2.6 Kruskal 求最小生成树

**为什么用 Kruskal 而不是 Prim**：两者结果相同（都是 MST，若有等权边则都是最优解之一），但 Kruskal 的"按边权排序 + 并查集"更直观地体现**"先铺最短的路段"**这个工程直觉，动画演示效果也更好（边的生长顺序就是真实铺设顺序）。本项目**两套都实现，用 Prim 对拍验证无 bug**。

```python
def kruskal(nodes, edges):
    parent = {v: v for v in nodes}
    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]   # 路径压缩
            x = parent[x]
        return x
    tree, total = [], 0.0
    for w, u, v in sorted(edges):            # O(E log E)
        ru, rv = find(u), find(v)
        if ru != rv:                         # 不成环才加入
            parent[ru] = rv
            tree.append((u, v, w))
            total += w
            if len(tree) == len(nodes) - 1:
                break
    return tree, total
```

**复杂度**：排序 $O(E\log E)$ + 并查集 $O(E\alpha(V))$，总计 $O(E\log E)$。
$E = \binom{46}{2} = 1{,}035$，排序与合并都在毫秒级。

**实测结果**（45 个供水目标 + 水源；边数 = 需求点数，即 46）：

| 指标 | 数值 |
|---|---|
| MST 边数 | 45 |
| 路网加权总长 | **8,115.9 m** |
| 管道实长（合并重叠段前） | 7,237.2 m |
| 最大树深 | 18 层 |
| 分支点 | 13 个 |

> 注：上表为**全部 45 个供水目标**同时求解的结果，已由 `06_代码/build_bundle_v2.py` 一次算出，不需要再叠加。"仅学生公寓"的对照口径为 MST 1,988.8 m / 管道 1,833.9 m / 2,130.5 m3/d。

**对照实验（方案对比，答辩重点）**：

| 方案 | 总长 | 相对 MST | 说明 |
|---|---|---|---|
| **MST（Kruskal，沿路网）** | **8,115.9 m** | 1.00× | 推荐方案 |

| 星形（每楼单独从水源引管） | **40,960.8 m** | 5.05× | 最基本方案，作为"省了多少"的基准 |

### 2.7 树形 DP：管径分配与流量累加

MST 给出拓扑后，还有第二个问题：**每段管子要多粗**。

**物理规律**：水从水源流向各楼，一棵树上越靠近根的管段，要通过越多的水（子树需求之和）：

$$q(u \to v) = \frac{\sum_{t \in \text{subtree}(v)} d_t}{86400} \times K_h \quad (\text{L/s})$$

**树形 DP（一次 DFS 后序完成）**：

```python
def pipe_sizing(root, adj):
    flow, order = {}, []
    def dfs(u, parent):
        q = demand.get(u, 0.0)          # 节点自身需求
        for v, w, eid in adj[u]:
            if v == parent: continue
            q += dfs(v, u)              # 子树需求向上累加
            order.append(eid)           # 后序：先定子边再定父边
        flow[u] = q
        return q
    dfs(root, -1)
    for eid in order:                   # 自叶向根
        q = flow[child_of[eid]] / 86400 * Kh
        dn[eid] = pick_dn(q)            # 按经济流速定管径
    return dn
```

**管径选取**（经济流速法）：

$$A = \frac{q}{v}, \quad D = \sqrt{\frac{4A}{\pi}}, \quad \text{取标准 } DN \ge D, \; v = 1.0\ \text{m/s}$$

标准管径档次：DN15/20/25/32/40/50/65/80/100/125/150/200/250/300/350。

**实测管径-长度分布**：

| DN | 350 | 300 | 250 | 200 | 125 | 100 | 80 | 65 | 50 | 40 |
|---|---|---|---|---|---|---|---|---|---|---|
| 长度 m | 92.9 | 340.5 | 634.5 | 339.1 | 151.6 | 165.3 | 105.6 | 269.8 | 163.0 | 1,155.7 |

**解读**（这段要写进报告，体现"算出来的东西有物理意义"）：
- 主干（DN300–350）只有 **433 m**，占 12.7%，但承担了绝大部分流量——符合"主管短而粗"的工程规律；
- DN40 支管 1,155.7 m 最长，都是各楼前的接户段——**这就是 DN40 占比高的原因，不是算法错了**；
- 管径随树深增大而变粗，验证了 DP 累加逻辑是对的。

**造价估算**：

$$\text{Cost} = \sum_{\text{管段}} \ell_e \cdot \text{单价}_{DN(e)}$$

单价参考市政给水管道综合单价量级（含管材、土方、接口、恢复），DN40≈80 元/m 到 DN350≈1,800 元/m 线性插值。实测总造价约 **468.3 万元**。

> 单价是**量级估算**，用于方案横向比较，不是报价。

### 2.8 三个算法怎么串起来（答辩用的"故事线"）

```
Dijkstra  →  把"距离"变成真实的沿路网距离     （可复现：63 次最短路）
   ↓
Kruskal   →  在真实距离上求最优连通拓扑        （可验证：与 Prim 对拍）
   ↓
树形 DP   →  把"拓扑"变成"能施工的管子"        （可解释：越靠根越粗）
```

**每个算法的输出都是下一个的输入**，不是三个孤立的小练习。这是本项目区别于"教科书例题"的地方。

## 3 加分项：让方案从"能跑"到"有深度"

### 3.1 多水源（Forest MST）

校园真实情况可能有多个市政接入点。此时问题变成**最小生成森林**：在需求点图上做 MST，但可以预留 $k$ 条"水源连接边"。

实现：把 $k$ 个水源都加入节点集，跑 MST 后检查是否每个水源都被用到；若某个水源未连边，说明在该拓扑下不需要它（或需强制加约束）。可对比 $k=1,2,3$ 的总长与最大树深。

### 3.2 容量约束（度约束 MST）

主干管有最大流量限制（如 DN350 对应 $q \le 100$ L/s）。若某子树流量超限，需要：

- 方案 A：拆分成两条并联支管（**并联管路水力计算**，$h_f = S q^2$，两条并联满足 $\sum q_i = q$）；
- 方案 B：把该子树的下游节点改为从另一条最近的主干接入。

这属于**度约束最小生成树（Degree-Constrained MST）**，本身是 NP-hard，可用贪心 + 局部搜索近似。这是"算法课拔高"的好素材。

### 3.3 分期建设（DP / 背包思想）

若预算有限（如只能先投 60 万），应该先铺哪些管？

把每条 MST 边看作一个"项目"，价值 = 覆盖的需求点数 × 需求水量，成本 = 该边长 × 单价。**这正好是 0-1 背包**：

$$\max \sum_i v_i x_i \quad \text{s.t.} \sum_i c_i x_i \le B, \; x_i \in \{0,1\}$$

约束：选中的边必须能组成连通子树（否则改造成"按深度分层的树形 DP"）。这是**动态规划在树上的经典应用**（树形背包），能把课程里的 DP 知识用上。

### 3.4 与已知解的对比（最优性讨论）

| 对照 | 做法 | 用途 |
|---|---|---|
| 直线 MST | 忽略路网 | 给出理论下界，说明路网约束的代价 |
| 星形 | 每楼独立 | 给出朴素方案，说明 MST 的收益 |
| Prim | 另一实现 | 与 Kruskal 对拍，证明实现正确 |
| 随机删边 + 重连 | 2-opt 局部搜索 | 检验 MST 是否已无可改进空间 |

## 7 可视化方案：怎么把结果画成"立体结构图"

### 7.1 先看原型（已验证可行）

`docs/fig/viz_25d.png` 是由当前注册表直接生成的 2.5D 成图（61 个建筑群全部按 `scripts/groups.py` 的名称标注）：建筑按楼层高度挤出成立体块、按类别着色；管道按管径着色并加发光描边；**每栋供水建筑都单独画出接户三件套**——路边青色圆环是接入点（tee），青色虚线是接至楼体的支管，楼体上的黄色竖线是立管，立管上每个小点是该层出水口（层高 3.2 m）；右上角统计面板；页脚管径与类别图例；底部标出市政接入点。这套东西**全部由一个 HTML 文件生成**，不依赖任何前端框架，可以直接用浏览器打开、投屏答辩。

> 为什么不能"只在主路上画一笔带过"：问题在于**一根主管道只是路网上的线，它本身不说明"这栋楼怎么喝到水"**。方案的工程可读性要靠接户点补齐——从哪条路接出来、接了几米、立管多高、第几层取水，这些是施工图必须交代的内容，也是答辩时"你想过实际怎么接吗"的答案。悬停任意建筑即可看到该楼的支管长度、来源路名与逐层出水口径。

![2.5D 等轴测方案图](fig/viz_25d.png)

### 7.2 四种方案对比（选型依据）

| 方案 | 效果 | 实现成本 | 适合什么 |
|---|---|---|---|
| **A. 2.5D 等轴测 SVG**（推荐主选） | 建筑挤出、管径着色、可动画 | **低**：纯 Python 生成单文件 HTML | 答辩演示、报告插图 |
| B. 平面 GIS 图 + 卫星底图 | 最真实、最像工程图 | 低 | 论文正文主图（要坐标、要可核对） |
| C. Three.js 真 3D | 可自由旋转缩放，最"炫" | 中高：需 CDN、需处理模型 | 加分展示（可选） |
| D. D3 力导向网络图 | 突出"树"的拓扑结构 | 中 | 讲解 MST 结构、展示树深 |

**结论：A + B 必做，C 选做，D 作为算法讲解的辅助图。**

理由：答辩看的是"**结论是否可信**"而不是"渲染是否好看"。B 保证可信（能对到真实地图），A 负责生动（立体感、动画），C 是锦上添花但容易拖时间。

### 7.3 2.5D 的实现要点（可直接照做）

**① 投影公式**（等轴测近似：绕 Z 轴旋转 θ，再沿 Y 方向压扁并抬高）

$$u = x\cos\theta - y\sin\theta, \qquad v = -(x\sin\theta + y\cos\theta)\cdot T - z$$

本项目实测参数：$\theta = -14°$，压扁系数 $T = 0.80$，$z$ 为高度（米）。

**② 画家算法**：把所有建筑按"质心在屏幕上的 $v$ 坐标"排序，从远到近绘制，后画的盖住先画的。每个建筑的侧面按"与视线夹角"做明暗（本项目 `shade = 0.62 + 0.34·|cos(角度 − θ)|`），顶面用纯色 + 浅色描边。

**③ 视图自适应**：把 `viewBox` 拟合到"建筑 + 水源"的包围盒，**不要**拟合到整张路网——否则校园外市政道路会把画面拉得很大、校区只剩中间一小块（第一版就踩了这个坑，改完校区充满画面）。

**④ 管道图层顺序**：道路（最底）→ 建筑 → 管道（最上，带发光描边）。管道必须在建筑之上，否则会被楼挡住。

**⑤ 动画**：
- **铺设生长**：按 MST 加边的顺序给每条管段 `stroke-dasharray` 从 0 到全长做动画，一条条"生长"出来——直观展示 Kruskal 的贪婪顺序；
- **水的流向**：在管段上叠一层虚线，`stroke-dashoffset` 匀速递减，视觉上就是水流；
- **悬停信息**：`<title>` 标签即可实现零成本 tooltip（楼名/层数/面积/日用水量/管径/流量）。

### 7.4 平面图（方案 B）要点

- 底图用高德卫星瓦片拼接（**必须做 WGS-84 → GCJ-02 转换，否则整体偏 511 m 东、137 m 北**）；
- 建筑轮廓画 OSM 多边形（WGS-84 原始数据，转成 GCJ-02 后叠加）；
- 管道按管径着色 + 线宽分级；
- 标注水源、主要节点、管径图例、比例尺、指北针；
- 角标注明数据来源（© OpenStreetMap contributors / © 高德地图）。

> 这个流程本轮已经跑通过：`docs/fig/fig3_mst_scheme.png` 就是同一套数据画的 2D 方案图，坐标转换与叠加都验证无误。
