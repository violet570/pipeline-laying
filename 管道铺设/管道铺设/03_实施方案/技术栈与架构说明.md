## 1. 现状：已经跑通的原型

原型只用 **Python 标准库** 跑完了「数据 → 图算法 → 出图」全链路，没有任何第三方依赖（除 Pillow 用于位图拼接与截图标注）。这意味着整套逻辑可以被完整移植，不存在被某个库锁死的问题。

| 环节 | 原型实现 | 文件 |
|---|---|---|
| 原始数据抓取 | Node.js + `fetch`，Overpass API 分块拉取 + 重试 | `fetch_osm.js`、`fetch_verify.js`、`fetch_full_buildings.js` |
| id 校验 | Node.js，逐 id 回查 + 地理范围断言 | `validate_ids.js` |
| 建筑注册表 | Python，纯数据表（唯一真源） | `groups.py` |
| 路网图构建 / Dijkstra / Kruskal / 树形 DP | Python，纯标准库（`heapq`、`math`、`json`） | `build_bundle_v2.py` |
| 接户点计算 | Python，点到线段投影 + 多边形距离 | `add_service_points.py` |
| 手描广场环路接入 | Python，连通分量切分 + 顶点吸附 | `plaza_road_trace.py`、`connect_plaza_ring.py`、`merge_plaza_roads.py` |
| 2.5D 等轴测出图 | Python 生成单文件 HTML + SVG | `viz_25d.py` |
| 位图拼接 / 校验图 | Python + Pillow | `make_figures.py`、`fig_*.py` |
| 页面截图 | headless Chrome `--screenshot` | 命令行 |

**原型的性能实测**（45 个供水目标）：构建图 + 46 次 Dijkstra + Kruskal + 树形 DP 全流程在普通笔记本上**秒级完成**，页面首帧渲染 61 个建筑群 + 188 段管道无卡顿。

> 结论：这套问题的规模（约 1000 节点、1100 边、45 个目标）**远低于需要专业图论库的量级**。自实现 Dijkstra/Kruskal 不仅够用，而且利于答辩时讲清楚每一步。

## 2. 正式实现的技术栈建议

### 2.1 技术选型总表

| 层 | 推荐 | 备选 | 选择理由 |
|---|---|---|---|
| 计算/数据后处理 | **Python 3.11+**，标准库为主 | `networkx`（图算法）、`shapely`（几何）、`pyproj`（坐标）、`numpy` | 算法规模小，自实现即可；若想省时间可用 networkx 对拍，但答辩时自实现更说得清 |
| 数据格式 | **JSON**（`pipeline_bundle.json`）+ GeoJSON | SQLite | JSON 可直接被前端 `fetch`，无需后端；GeoJSON 便于在 QGIS 里检查 |
| 前端框架 | **原生 HTML + SVG（单文件）** | Vue 3 / React + D3 | 无构建、无依赖、可直接投屏；SVG 天然支持 `stroke-dasharray` 动画和 `:hover` |
| 地图库 | **Leaflet 1.9**（可选引入，用于切底图） | MapLibre GL JS、OpenLayers | Leaflet 体量小、API 简单，切卫星/路网底图最省事；纯 SVG 方案则完全不用地图库 |
| 定位投影 | **自实现 Web Mercator**（约 20 行） | `proj4js` | 只需 z17/z18 两级，自实现足够；GCJ-02 转换必须自实现（见 §4） |
| 底图瓦片 | **高德栅格瓦片**（免 key，`webrd01`/`webst01`） | 高德 JS API、天地图、Esri | 实测本区域可直连下载；高德 JS API 需要 key 且是矢量切片，反而不便离线 |
| PNG 导出 | **Chrome headless `--screenshot`** | Puppeteer / Playwright | 已跑通；注意中文路径必须先拷到 `%TEMP%` |
| 动效 | **CSS `@keyframes` + SVG `stroke-dashoffset`** | requestAnimationFrame 手写 | 已跑通，水流虚线效果稳定；复杂生长动画可用 rAF 控时序 |
| 文档 | Markdown → 可转 PDF（Pandoc / Word） | — | 报告与图件同源，改数字不用两处改 |

### 2.2 为什么不用 Three.js 做真 3D

- **收益有限**：管道埋在地下，真 3D 里最有价值的「立体感」在建筑体块上，等轴测投影（2.5D）已经给足；管道本身在任何视角下都是一条线。
- **成本明显**：Three.js 需要处理光照、材质、相机控制、标注贴图，代码量约为 SVG 方案的 3~5 倍，且截图与投屏更麻烦。
- **答辩友好度**：SVG 是 DOM，悬停/点击/改颜色都是一行 CSS；Three.js 里做同样的事要写射线拾取。
- **建议**：主展示用 2.5D SVG；若想加分，可以额外做一个 Three.js 的「鸟瞰旋转」演示页作为**附加彩蛋**，不作为主交付。

## 3. 系统架构（建议的正式实现）

```
┌──────────────────────────────────────────────────────────────┐
│  数据层  04_数据/                                             │
│   raw/        OSM 原始 JSON（只读，禁止改动）                  │
│   derived/    pipeline_bundle.json（计算产物）                │
└───────────────────────────┬──────────────────────────────────┘
                            │ 构建脚本（一次跑完）
┌───────────────────────────▼──────────────────────────────────┐
│  计算层  build/  （Python）                                   │
│   1. 读注册表 groups.py → 建筑名录/分类/层数                    │
│   2. 建路网图（节点合并 + 边权 + 接户点断裂插入）               │
│   3. 求解：Dijkstra / Kruskal MST / 树形 DP 定管径              │
│   4. 输出 bundle.json + 统计报告                               │
└───────────────────────────┬──────────────────────────────────┘
                            │ 静态 JSON（无后端）
┌───────────────────────────▼──────────────────────────────────┐
│  展示层  web/index.html （单页，离线可用）                     │
│   ┌─────────────┬──────────────────────┬──────────────────┐  │
│   │ 控制面板      │  画布（SVG 2.5D/平面） │  统计与对比面板     │  │
│   │ 起点/终点选择 │  建筑体块 + 路网       │  MST / 直线 / 星形  │  │
│   │ 规划模式      │  管道 + 接户点         │  管径分布 / 造价    │  │
│   │ 参数滑块      │  动画层（生长/水流）    │  数据告警           │  │
│   └─────────────┴──────────────────────┴──────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

**关键设计决策**：**没有后端**。所有求解在构建期完成，前端只读一份 JSON。理由是：
- 交互需求（改起点/终点/参数后重算）可以在前端用 JS 直接跑 Dijkstra（1000 节点只需毫秒级），不需要服务器；
- 答辩时可以断网演示，不怕现场网络出问题；
- 部署零成本，双击 `index.html` 就能看。

> 例外：如果要支持「现场改用水指标后重算管径」，这也在前端做（树形 DP 是 O(V) 的，很快）。

## 4. 坐标系与底图对齐（最容易踩的坑）

这是整个项目**唯一必须严格处理**的工程细节。

| 数据源 | 坐标系 | 说明 |
|---|---|---|
| OpenStreetMap | **WGS-84** | 建筑轮廓、道路几何全在此系 |
| 高德（Amap） | **GCJ-02**（火星坐标） | 瓦片、POI、API 全部 GCJ-02 |
| 百度 | BD-09 | 若用百度底图需 GCJ→BD 二次偏移 |
| Google 卫星 | WGS-84 | 但被墙，实际不可用 |
| Google 道路/POI | GCJ-02 | 厂商不同图层不同坐标系，会错位 |

**本项目实测偏移量**（西校区中心）：WGS-84 → GCJ-02 约 **东偏 511 m、北偏 137 m**，合成位移 **529 m**。

而宿舍区东西跨度只有约 584 m——**不转换的话，整张管网会整体飞出校园**。

### 4.1 计算与展示的分工

- **所有计算在 WGS-84 下进行**，量距用局部切平面近似（`m_per_deg_lat = 111320.0`，`m_per_deg_lon = 111320 × cos(纬度)`），在本项目尺度（约 2 km × 1.5 km）误差 < 0.1%，可忽略。
  - 若要更严格，用 **EPSG:32650（UTM 50N）**，`pyproj` 一行转换。
- **只在出图给高德底图时**，把 WGS-84 顶点转成 GCJ-02 再落像素。

### 4.2 GCJ-02 转换代码（可直接抄）

```python
import math
A = 6378245.0            # 克拉索夫斯基椭球长半轴
EE = 0.00669342162296594323

def _tlat(x, y):
    r = -100.0 + 2.0*x + 3.0*y + 0.2*y*y + 0.1*x*y + 0.2*math.sqrt(abs(x))
    r += (20.0*math.sin(6.0*x*math.pi) + 20.0*math.sin(2.0*x*math.pi)) * 2.0/3.0
    r += (20.0*math.sin(y*math.pi) + 40.0*math.sin(y/3.0*math.pi)) * 2.0/3.0
    r += (160.0*math.sin(y/12.0*math.pi) + 320*math.sin(y*math.pi/30.0)) * 2.0/3.0
    return r

def _tlon(x, y):
    r = 300.0 + x + 2.0*y + 0.1*x*x + 0.1*x*y + 0.1*math.sqrt(abs(x))
    r += (20.0*math.sin(6.0*x*math.pi) + 20.0*math.sin(2.0*x*math.pi)) * 2.0/3.0
    r += (20.0*math.sin(x*math.pi) + 40.0*math.sin(x/3.0*math.pi)) * 2.0/3.0
    r += (150.0*math.sin(x/12.0*math.pi) + 300.0*math.sin(x/30.0*math.pi)) * 2.0/3.0
    return r

def wgs2gcj(lon, lat):
    """WGS-84 -> GCJ-02（叠加到高德底图用）"""
    dlat = _tlat(lon - 105.0, lat - 35.0)
    dlon = _tlon(lon - 105.0, lat - 35.0)
    rad = math.radians(lat)
    magic = 1 - EE * math.sin(rad) ** 2
    sq = math.sqrt(magic)
    dlat = (dlat * 180.0) / ((A * (1 - EE)) / (magic * sq) * math.pi)
    dlon = (dlon * 180.0) / (A / sq * math.cos(rad) * math.pi)
    return lon + dlon, lat + dlat

def gcj2wgs(lon, lat):
    """GCJ-02 -> WGS-84（把高德 POI 坐标转回计算坐标系）"""
    # 一次近似即可（误差 < 0.5 m）；若要精确可迭代 3~5 次
    glon, glat = wgs2gcj(lon, lat)
    return lon - (glon - lon), lat - (glat - lat)
```

### 4.3 Web Mercator 像素换算

```python
Z = 18                        # 瓦片层级
N = 2.0 ** Z * 256.0          # 该层级总像素宽

def ll2px(lon, lat):          # 经纬度(GCJ-02) -> 全局像素
    x = (lon + 180.0) / 360.0 * N
    lat_r = math.radians(lat)
    y = (1.0 - math.log(math.tan(lat_r) + 1.0/math.cos(lat_r)) / math.pi) / 2.0 * N
    return x, y

def px2ll(x, y):              # 全局像素 -> 经纬度(GCJ-02)
    lon = x / N * 360.0 - 180.0
    lat = math.degrees(math.atan(math.sinh(math.pi * (1 - 2*y/N))))
    return lon, lat
```

## 5. 坐标量测工作流（新增或修正一栋楼时用）

这是本项目反复迭代出的**唯一可靠流程**，务必照做：

1. **先查 OSM 有没有**  
   `python scripts/query_box.py <south> <west> <north> <east> out.txt`  
   列出该框内所有建筑的 name / way_id / 面积 / 中心 / bbox。有就直接用 OSM 轮廓，不要量测。

2. **OSM 没有 → 出像素网格图**  
   `python scripts/measure_grid.py <lat0> <lon0> <hw> <hh> <out.jpg> "<标题>" [放大倍数]`  
   脚本会打印 `ox=... oy=...`（裁剪窗口在 z18 下的全局像素原点），**记下来**。

3. **在图上人工读建筑外框**（深色屋顶的四个角），用 25 px 网格数字辅助读数。

4. **换算成经纬度**  
   `python scripts/px2ll.py <ox> <oy> "x0,y0,x1,y1"`  
   输出 bbox / 中心 / 尺寸 / 面积。

5. **必做：回画一张校验图，用眼睛确认框套住了屋顶**  
   历史上跳过这一步，导致过 20~40 m 的系统偏差、甚至框到了旁边的停车场。

**经验教训**：
- 用经纬网目视估读偏差可达 20~40 m；**像素网格读点 + px2ll 反解可以到 ±1.5 m**。
- 自动分割（按亮度阈值找连通域）在屋顶亮度不均 + 有阴影时会失败，**人工读点反而更稳**。
- 图片路径含中文时，`Pillow` 保存前要确认目录存在，否则报 `FileNotFoundError`。

## 6. 数据质量与已知边界

| 项 | 状态 | 处理方式 |
|---|---|---|
| 建筑轮廓 | 50 个来自 OSM（高质量矢量） | 直接使用 |
| 建筑轮廓 | 11 个来自影像量测（bbox 矩形代理） | 面积取实测值而非矩形面积；个别的框偏大可能包住旁边道路 |
| 建筑位置 | 10 组（Y01–Y11）只有楼名无坐标 | **不参与计算**，页面标为「待定位」 |
| 道路 | 148 条 OSM + 5 条用户手描（圆形广场环路） | 手描部分标 `source=user_trace`，图上用不同颜色区分 |
| 层数 | 仅 9 株有 OSM `building:levels`，其余按类别默认 | 报告中如实标注 `levels_src` |
| 水源 | OSM 无给水泵房数据 | 用南主门市政接入点**假设**，页面上必须写「假设」 |
| way id 污染 | 曾发生 5 个 id 指向美国北达科他州道路 | 已建立 `validate_ids.js` 校验流程，保留 |

**报告的写法要求**：凡是假设、量测、推断的数据，都必须能追溯到来源并在图/表中标出。这是本项目评分上的加分项，也是学术诚信的底线。

## 9. 若要换一套技术栈，怎么迁移

| 假设你改用… | 需要重写 | 可以直接复用 |
|---|---|---|
| Vue 3 + D3 | 展示层（约 600 行 JS） | 全部 Python 计算、bundle.json |
| Three.js | 展示层的 3D 渲染部分 | 同上，且 `viz_25d.py` 里的投影公式可直接迁移成相机矩阵 |
| Leaflet 做平面图 | 展示层坐标映射 | 同上，瓦片 URL 与 `wgs2gcj` 直接复用 |
| 加后端（Flask/FastAPI） | 把 Dijkstra/Kruskal 包成接口 | 算法函数原样搬过去 |
| 换更大范围（如整个燕大东西校区） | 数据抓取 bbox + 路网规模 | 架构不变；规模到 10 万节点时才需要换 networkx/scipy |

**核心结论：数据与算法的边界是清晰的。** 换展示层不影响数据，换数据源不影响算法。这是这个项目结构上最值得保留的部分。
