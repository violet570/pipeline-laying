# 燕山大学西校区管道铺设项目
## 方案可行性论证 + 技术实现方案（技术栈 / 架构 / 实施路线）

> 交付性质：**可行性评估 + 技术方案设计**。本文不追求给出完整程序，而是回答两件事：
> ① 这套"真实校园地图 + 最小生成树 + 立体/平面可视化"的方案到底可不可行、风险在哪；
> ② 如果可行，应该用什么技术栈、按什么架构和步骤落地。
> 仓库里已有的抓数脚本、算法脚本、验证图（见附录 A）只是**可行性证据**，不是最终程序。
>
> 数据来源：OpenStreetMap（ODbL）2026-08-10 快照；高德卫星/路网瓦片（仅对照与署名）。所有结论标注【事实】/【推断】/【假设】。

## 0. 一句话结论

**可行，评级「可行（B+）」：数据能拿到、算法能跑通、可视化能落地，且不需要 Google 地图。**
关键事实链：

- 【事实】**Google 地图上没有可直接使用的"西校区逐栋公寓"标注数据**，且 Google 中国图层的道路（GCJ-02）与卫星（WGS-84）错位数百米，不能当坐标基准——但它不是必需品，**用 OSM 就能拿到 34 栋公寓的逐栋真实轮廓坐标**。
- 【事实】算法已端到端跑通：34 栋公寓 → 路网图（955 节点 / 1067 边）→ Dijkstra → Kruskal MST = **加权长 3671.5 m、管段实长 3418.1 m、DN40–DN350、估算造价 104.2 万元**，并生成了 2D 方案预览图与"OSM 轮廓叠高德卫星"的校验图（图 2、图 3）。
- 【事实】可视化路线成熟：单文件 HTML + SVG 2.5D + 动画，零依赖、可离线答辩、可截图成图；进阶可用 Three.js / MapLibre + 真实底图。
- 【推断/假设】主要风险不在算法，而在**数据细节打磨**（个别楼栋接户点绕行）和**假设的透明度**（水源点、用水指标、造价单价）。这些都可以通过"明确声明 + 敏感性分析"变成报告亮点，而不是硬伤。

## 1. 你的问题的直接回答：Google 地图有没有西校区各公寓楼的位置？

### 1.1 结论（对应调研报告 `report/google_maps_verification.md`，总评级 B）

| 问题 | 结论 | 证据强度 |
|---|---|---|
| Google 地图有没有 1-A…13-B2 这类**逐栋公寓 POI**？ | **没有找到任何直接证据支持"有"**。本环境无法直连 Google（瓦片/域名全部 fetch failed），只能靠间接证据：Google 中国区数据由高德供应且无测绘资质（泰伯网）；uniRank 的燕大页面只有 main campus 级示意图；Google 街景在中国大陆无城市级覆盖 | 间接但一致（B 级） |
| Google 有没有**卫星影像**？ | **有**（地球在线、Google Earth 均可看燕大卫星图），但本环境**无法验证该校区影像的分辨率/年份**；Google Earth 全球多数地区 0.3 m 级 | 存在性可信，质量待验证 |
| 就算有，能拿来当数据源吗？ | **不能直接当基准**：Google 中国矢量/道路层是 GCJ-02、卫星层是 WGS-84，两层错开数百米；而 OSM 轮廓是 WGS-84，**可以直接叠 Google 卫星图**（只需转换我们的数据） | 高（多来源一致） |
| 国内图商有没有逐栋数据？ | **有**。城市吧（百度底图）能查到"燕山大学西校区学生公寓13A"这类逐栋 POI，说明逐栋数据在国内图商手里，只是接口需 key/有反爬 | 高（直接反证） |

一句话：**"Google 只有几个关键地点标注、没有实体地图"这个直觉基本正确**——Google 上能用的只有卫星影像和校区级轮廓，逐栋楼的位置得靠你自己从卫星图描或换数据源。

### 1.2 对你项目的含义

- **不需要 Google 也能做**：真实数据源改用 OSM（OpenStreetMap），实测直接给出 34 栋学生公寓的逐栋轮廓与名称（1-A…13-B2 + 4 栋未命名）。
- Google 卫星图/高德卫星图/官方校园地图的正确用途是：**展示时叠加对照、人工校核、报告插图**，而不是作为坐标来源。
- 如果答辩时被问"数据哪来的"，标准答案是：**OSM 矢量数据（WGS-84，ODbL 署名）+ 官方校园地图人工比对 + 高德卫星截图对照（署名）**，并说明坐标系转换——这比"我对着 Google 描的"可信得多。

1. **6-A 标签错误**：`building=university` 但名称是 `6-A`，实为学生公寓 → 用"名称正则 + 组团面包含"规则纠正。

### 2.3 坐标系方案（必须做，否则图会"飞"）

【事实】国内各图商坐标系不同，实测偏移量很大：

| 坐标系 | 使用者 | 与 WGS-84 的关系 |
|---|---|---|
| WGS-84 | OSM、GPS、Google 卫星层 | 基准 |
| GCJ-02（火星坐标） | 高德、腾讯、Google 中国道路层 | 西校区中心实测 **东偏 511 m / 北偏 137 m（合 529 m）** |
| BD-09 | 百度 | 约东偏 1055 m / 北偏 839 m |
| CGCS2000 | 天地图 | ≈ WGS-84 |

**方案约定**：
- **计算统一用 WGS-84**，米制投影用 **EPSG:32650（UTM 50N）**；若不想装 pyproj，可用"等距近似"（本项目实测误差可忽略）：`x = (lon - lon0)·111320·cos(lat0)`，`y = (lat - lat0)·111320`。
- **展示时才转换**：把 OSM 的 WGS-84 数据转成 GCJ-02，再叠高德卫星/路网瓦片；反方向（底图坐标当数据用）**绝对不能做**。
- 图 2 就是这条链路的验证：OSM 建筑轮廓转换后叠加高德 z18 卫星图，逐栋吻合 → 说明**坐标转换和底图叠加都可实现**。

![图2 高德卫星 z18 + OSM 建筑轮廓（WGS-84→GCJ-02）叠加校验](fig/fig2_dorm_satellite_overlay.jpg)

*图 2：红色 = OSM 学生公寓轮廓，青色 = 其他建筑，均已从 WGS-84 转换到 GCJ-02 后叠加到高德卫星瓦片上。逐栋吻合，说明"OSM 数据 + 底图叠加"这条可视化路线成立。*

## 3. 算法可行性：作业核心，已端到端跑通

### 3.1 问题形式化

把校园道路网建成带权无向图：

- 顶点 `V` = 道路节点（交叉口、路段端点、建筑接户投影点）
- 边 `E` = 相邻节点间的道路段
- 边权 `w = 长度 × 敷设难度系数`（主干道 1.0，支路 1.15，步道/自行车道 1.3~1.6；可按"是否允许开挖"调整）
- 目标：选边集 `T ⊆ E`，使 `{水源} ∪ 公寓` 全连通，且 `Σ w` 最小 → **这是图上的 Steiner 树问题的启发式解**（把水源和每栋楼投影到路网后，退化为"路网最短路完全图上的 MST"）

> 为什么不是"直接连楼与楼的直线"：管道必须沿可开挖道路走。直线 MST（1874 m）只是理论下界，不能施工；星形（27309 m）是每栋楼单独接管的对照上界。**沿路网 MST 才是折中合理方案**——这正好是算法设计课要的"模型合理性"论述。

### 3.2 算法流程（6 步，已验证）

```
Step 0 数据清洗
  校园边界多边形裁剪 → 剔除东校区/一中/周边小区(31栋)
  建筑分类：dormitory / canteen / teaching / office / library / hospital / lab …
  公寓组团归组（13 个组团面 + 最近组团兜底）
Step 1 建路网图
  highway 白名单过滤(steps/construction 排除) → 全局节点坐标合并(共享节点去重)
  E 条边，边权 = 长度 × 难度系数
Step 2 建筑接入（Steiner 化）
  建筑质心 → 投影到最近路段 → 在投影点打断边、插入接户节点
  （最大接路距离 86.6 m；超过 250 m 的视为未接入）
Step 3 两两最短路
  对每个目标节点跑一次 Dijkstra（二叉堆）→ 距离矩阵 D[35][35]
Step 4 Kruskal 求 MST
  并查集 + 按距离排序；得到 34 条树边
Step 5 流量与管径
  以水源为根 BFS → 树深、父子关系 → 子树需求累加（末梢→根）
  节点流量 Q = 日用水量；设计秒流量 q = Q·Kh/86400（Kh=2.5）
  管径 d = √(4q/(π·v))（v=1.0 m/s）→ 向上取标准 DN（40/50/65/80/100/125/150/200/250/300/350）
  造价 = Σ 长度 × 单价(DN)
Step 6 输出
  管段清单（含铺设层级 order）、统计面板、MST 边序（可用于动画）
```

### 3.3 已跑通的真实结果（34 栋公寓方案，可直接写进报告）

| 指标 | 结果 |
|---|---|
| 目标节点 | 34 栋公寓（+ 水源 1 个） |
| **MST 加权总长** | **3671.5 m** |
| 管段清单实长（合并后） | 3418.1 m |
| 对照：直线 MST（理论下界） | 1874.2 m |
| 对照：星形供水（每楼单独接管） | 27309.0 m |
| 日用水量 | 2287.2 m³/d |
| 设计总流量（Kh=2.5） | 66.18 L/s |
| 管径范围 | DN40 – **DN350** |
| 分支点（≥3 度） | 9 个 |
| 最大树深 | 18 层（从水源沿树向外） |
| 估算造价 | **104.2 万元**（含管材/土方/接口的综合单价粗估） |

完整清单见 `data/derived/build_report.txt`；结构化结果见 `data/derived/pipeline_bundle.json`（可视化直接读这个）+ `data/derived/pipes.geojson`（可导入 QGIS）。

### 3.4 复杂度与实现代价

- 规模：`V=955`，`E=1067`，`k=35` 目标。Dijkstra 跑 35 次 ≈ O(k·(E log V)) ≈ 百万级操作；Kruskal O(E log E)。**Python 纯标准库秒级完成**，不需要任何大型依赖。
- 对比：如果节点更多（比如把全校 72 栋都接进来 + 多水源），也只需分钟级；不需要 GIS 服务器或图数据库。

### 3.5 已知问题与处理（写进报告的"模型讨论"是加分项）

1. **0 m 树边**：相邻的 A/B 栋（如 1-A/2-A）共用同一个接户节点 → MST 里出现 0 m 边。**处理**：报告中说明"共用接户点"，可视化里合并显示为一个节点，或按 10 m 最小支管长度修正。
2. **个别楼栋绕行偏大**：例如 12-A2 出现 1155 m 的 DN40 支管——因为"建筑质心投影到最近路段"落在了园区外侧道路，绕行费钱。**处理**：① 接户点加规则（优先选楼门口一侧、园区内道路）；② 允许"楼前支管直连"（从建筑到路网的直线段按 1.2 倍计入）；③ 报告中作为"启发式与真实工程的差异"讨论。
3. **MST 是理想模型**：真实管网还要考虑"主干—支管"两级布置、环状冗余、坡度/埋深、道路开挖许可、阀门井位置。**处理**：不硬做，而是在报告里加一节"模型局限 + 可扩展方向"，并用对照实验（直线 MST / 星形 / 不同水源位置）体现思考深度。
4. **0.6 m 级数据精度**：OSM 轮廓 + 投影接入的误差在米级，对"方案展示"完全够用；对施工不适用——报告里明确边界即可。

### 3.6 可选加分扩展（学有余力再做）

- 扩展目标：宿舍 + 食堂 + 服务楼 + 教学楼（36~40 目标），体现"多用户"。
- 敏感性：把 2025 年在建 7#~10# 新公寓加进需求，看管径/造价变化。
- 多水源：南门 vs 假设的清水泵房位置，对比 MST 长度与主干走向。
- 供热版：用已确认的换热站（锅炉房旧址/材料学院/大食堂/十组团/东北角）作为热源，做二次网 MST。
- 算法对比：Prim vs Kruskal vs Borůvka（同一结果，展示不同实现）；或加入"管径约束下的最小费用流"讨论。

## 4. 可视化可行性：从数据到"生动的立体图"

### 4.1 方案对比

| 方案 | 效果 | 开发成本 | 依赖 | 适用 |
|---|---|---|---|---|
| **单文件 HTML + 原生 SVG 2.5D**（推荐） | 斜轴测立体感、建筑挤出、管道动画、悬停信息 | 中（1~2 天） | 零依赖、可离线、双击即开 | 作业/答辩首选 |
| Three.js 真 3D | 自由视角、光照、飞线 | 中高 | 需要打包/服务器（或本地 file:// 加载 module 的坑） | 想要"炫"时 |
| MapLibre/deck.gl + 真实底图 | 地图感强、可叠卫星 | 中 | 需底图与坐标转换 | 展示"真实位置"时 |
| Cesium / Blender | 地球级 3D / 影视级渲染 | 高 | 重、非课程重点 | 不推荐 |

### 4.2 推荐实现：单文件 HTML + SVG 的 2.5D

**投影公式**（斜轴测，参数可调）：
```
θ = -20°（平面旋转角）
X = x·cosθ - y·sinθ
Y = x·sinθ + y·cosθ - z·scale      // z=建筑高度，向上为负 Y
```
**绘制顺序**（画家算法，先远后近）：
1. 底图（可选：卫星瓦片裁片 / 纯色地面 / OSM 路网）
2. 区域底色（水面、绿地、组团面）
3. 道路（按等级粗细/颜色）
4. 建筑：每个建筑 = 底面多边形 + 侧面四边形（只画朝向观众的 2 个面）+ 顶面；按屏幕 Y 排序绘制
5. 管道：按 `order`（从水源向外的铺设层级）分色/分粗细，末端 DN 细、主干 DN 粗
6. 节点/文字：水源星标、井位、楼名标签（可用 SVG `<text>` + 描边保证可读）

**动画**（答辩最出彩的部分）：
- **生长动画**：每条管段按 `order` 依次出现（`stroke-dasharray` 渐显），播放"从水源一路铺到每栋楼"的过程；
- **流动动画**：管道上叠加虚线 `stroke-dashoffset` 无限循环，模拟水在管中流动；
- **悬停/点击**：`<title>` 或 JS tooltip 显示 楼名/组团/层数/面积/日用水量/管径/流量；
- **图层开关**：2.5D / 平面切换、显示/隐藏 建筑/道路/管道/组团/卫星底图；
- **统计面板**：公寓数、MST 长、造价、管径分布（可直接画简单条形图）。

**关键参数**：世界坐标统一换算成米（WGS-84 → 本地米制），SVG viewBox 自适应缩放；建筑高度 = 层数 × 3.2 m；管道线宽按 DN 线性/平方根映射。

## 5. 技术栈设计

### 5.1 推荐技术栈（主选）

| 层次 | 技术 | 版本/说明 | 理由 |
|---|---|---|---|
| 语言 | **Python** | 3.11+（本机 3.13 已够） | 算法/数据处理生态好，课程通用 |
| 数据获取 | `requests`（或 `urllib`）+ **Overpass API** | 镜像 `overpass.openstreetmap.fr`，带 Referer、UA、重试、分块、本地缓存 | 免 key、免登录、数据全；可复现 |
| 几何处理 | 标准库 `math` + 自写点在多边形/投影/插点；可选 `shapely` + `pyproj` | 本项目已验证**纯标准库可实现** | 降低环境风险；老师电脑也能跑 |
| 算法 | **自实现** Dijkstra（`heapq`）+ Kruskal（并查集）+ 树遍历 | 约 300 行 | 课程要展示算法过程；`networkx` 只用来交叉验证 |
| 数据存储 | JSON / GeoJSON / CSV | 不引入数据库 | 作业规模不需要 PostGIS/SQLite |
| 可视化 | **HTML5 + 原生 SVG + 原生 JS** | 单文件、内嵌 JSON、离线可开 | 零依赖、易截图、答辩稳 |
| 可选增强 | D3.js v7（比例尺/坐标轴）、Three.js r160+（真 3D） | 按需 | 不加也能做完 |
| 底图 | 高德栅格瓦片（免 key）/ OSM 瓦片 / 官方校园图 | 需 WGS-84→GCJ-02 转换 + 署名 | 图 1、图 2 已验证 |
| 出图 | **Chrome/Edge headless** `--screenshot`（或 Playwright） | 本机已装 Chrome、Edge | 一键把 HTML 截成 PNG 进报告 |
| 动画导出 | Pillow 合成帧 → GIF；或录屏 → MP4 | Pillow 已装 | 报告/答辩视频 |
| 报告 | Markdown → Pandoc → PDF/Word | 或 python-docx（已装） | 排版快、可版本管理 |
| 版本管理 | Git | 已装 | 交作业留痕 |

### 5.2 最小可行集（1 天能搭起来，完全够交作业）

> Python（标准库）+ GeoJSON/JSON + 自实现 Dijkstra/Kruskal + 单文件 HTML/SVG + Chrome headless 截图

**不需要**：Web 框架、数据库、GIS 服务器、前端构建工具、云服务。作业评分看的是算法与展示，不是工程复杂度。

### 5.4 核心数据契约（前后端/脚本之间统一口径）

`pipeline_bundle.json` 建议结构（本项目已按此输出，可视化可直接消费）：

| 字段 | 内容 |
|---|---|
| `meta` | 标题、生成时间、坐标系、原点、每度米数、OSM 时间戳、水源点、假设列表 |
| `buildings` | 全部建筑：id/name/cat/group/levels/height/area/floor_area/demand/lat/lon/footprint |
| `dorms` | 34 栋公寓（含 group、demand、接路节点 nid） |
| `roads` | 道路折线（hw/name/pts[[lon,lat]…]） |
| `areas` | 区域面（组团/水面/绿地…） |
| `pipes` | 管段：a/b[[lon,lat]]、length、flow(L/d)、q_ls、dn、order(铺设层级) |
| `tree_edges` | MST 树边（u/v 节点 id、w、depth）——做生长动画用 |
| `stats` | 统计面板：公寓数、MST 长、管道长、管径分布、造价、对照方案长度等 |

> 所有坐标建议**统一输出 WGS-84 的 `[lon, lat]`**，可视化层再做米制投影和 GCJ-02 转换；不要在算法层混用坐标系。

## 9. 结论与建议

1. **方案可行**：三条腿——数据（OSM 实测 34 栋公寓）、算法（MST 已跑通，3671.5 m / 104.2 万元）、可视化（HTML/SVG 2.5D，底图叠加已验证吻合）——都成立。
2. **不要纠结 Google**：它给不了逐栋数据，还带 GCJ-02 偏移陷阱；把它降级为"卫星参照"，用 OSM 作为数据底座，是更稳、更专业的选择（答辩时还能作为"数据源对比"的亮点）。
3. **最该花时间的地方**：不是算法代码（已证明不难），而是 ① 接户点与数据细节的打磨；② 让报告"有理有据"（假设透明、对照充分、来源可查）；③ 做出一个能稳定演示的动画。
4. **建议下一步 3 件事**：
   - 按第 6 节 Day 1 把数据链路重跑一遍并核对 34 栋公寓清单（重点是 12/13 组团与"未命名公寓"）；
   - 用现成 `pipeline_bundle.json` 先做**平面图 + 管道生长动画**（最快出效果）；
   - 再升级 2.5D 挤出与卫星底图叠加，最后补报告中的假设/对照/调研章节。

> 本方案完全不需要 GPU、不需要服务器、不需要数据库；一台普通笔记本 + Python + 浏览器即可完成。
